Continuous operation

This file defines the orchestrator's implementation loop. Use it when the user starts or resumes continuous implementation. A request to answer a question, prepare a proposal, or run a bounded task does not by itself start this loop. Respect an explicit time limit, stop request, or narrower task scope.

.agents/glossary.md defines the work units; .agents/selection.md governs selection. .agents/review.md governs formal reviews.

Worker scheduling

Run one main orchestrator and two persistent implementation workers, each in a separate Git worktree. A span is one unit of implementation that a worker completes for delivery. A delivery consists of fixed commits and their evidence. Each worker implements and validates its own spans and periodically tells the orchestrator when a completed span is ready to merge. Only the orchestrator merges into the integration branch, runs combined validation, and publishes to main. Use one worker when only one independent goal is ready or resources permit only one. Do not add implementation workers above two without user approval. Read-only helpers do not own implementation.

The orchestrator owns the integration branch, main, GOALS.json, SCORE.tsv, review records, aggregate scoring, and publication. Workers own only their assigned source, focused tests, recipes, recordings, and local handoff files. Do not merge worker copies of the central ledgers. A worker proposes any new QUALITY.json area assignment; the orchestrator applies it.

Use scripts/worker-state.mjs to update .cache/worker-state.json. Give each worker the absolute path to that JSON file. Workers may record their own connection, turn state, assignments, scope expansions and deliveries. Only the orchestrator records integration, acceptance and publication. Do not edit the JSON by hand. Run scripts/worker-state.mjs with --help for the commands and required fields. Record each assignment, delivery, integration, validation, acceptance, publication, and pause when it happens. The command adds timestamps and tracks each task's reservations. Each reservation belongs to a task and records which worker may edit specified source functions or shared-state contracts. Release only the reservations for the task being accepted or parked. Parking puts work aside without discarding it.

The JSON file holds recoverable local coordination state. It does not establish source completion. Commit accepted source evidence to GOALS.json.

The initial assignment and the permission below to continue independently authorize a worker to implement a goal even when its copy of GOALS.json does not list that goal as open. The orchestrator handles goal opening, measurement, and closure one at a time so another worker's gains are not attributed to the wrong goal. Before giving a worker its first assignment, the orchestrator prepares .cache/span-context.json in that worker's worktree. Use the fields, source order, and line caps specified by nextSpan() and spanContext() in scripts/goal-log.mjs. Workers prepare later contexts using the same rules, without changing GOALS.json or waiting for the orchestrator to open the goal. Record queued goals at a safe commit boundary in the integration branch. Do not change the inputs of a checkpoint that is running.

Before starting work in a new worker or integration worktree, run node scripts/worker-worktree.mjs prepare --branch <assigned-branch> from that worktree. Use --help for recorder setup options. The command checks out the pinned C source and starts a fresh game with the worktree's private recorder. If it fails, fix the setup before starting work. Before any write, the worker verifies pwd, git rev-parse --show-toplevel, and its branch against the assignment. Every command, edit, and descendant agent uses that absolute worktree path. Never share a recorder installation.

Keep the same worker and worktree across deliveries. Use a fresh worker only for recovery or an explicit handoff, after determining which processes the previous worker owns. Do not routinely have implementation workers create further implementation workers.

Give each worker an initial span and permission to keep selecting independent work within the user's task bounds. After sending a delivery whose commits and evidence will no longer change, the worker chooses its next work under .agents/selection.md, "Seed continuation", and claims that scope with a worker-state assign event before editing. The command checks and reserves the scope in one locked update. If another worker owns it, the worker chooses independent work. After successfully claiming the scope, the worker proceeds without waiting for acknowledgement, merge, combined validation, CI, or the other worker.

Reserve functions and shared-state contracts. Do not reserve whole files indefinitely. Give each dependency shared by workers one owner. Keep reservations for pending deliveries; release or revise them when a delivery is integrated, reassigned, or deliberately parked. A worker must ask the orchestrator before editing another worker's reserved function or changing a shared contract. The worker continues independent work while that decision is pending.

Merge requests

Before initial dispatch or replacement, have the worker record a connect event from its assigned worktree. The orchestrator reads and acknowledges that connection before dispatching implementation.

At each completed span, the worker sends READY_TO_MERGE to the main orchestrator. The message is the merge request and must include the fields below. The worker does not perform the central merge itself. Send the request when the span has focused tests, lint, source evidence and required matching independent recordings. Do not wait for a timer or another worker. During a long-running span, the worker sends progress or blocker updates without claiming that incomplete work is ready.

Each request identifies the worker and worktree, base and delivery SHAs, exact commits to accept, dependencies on earlier deliveries, and changed paths and functions. Include commands and results, a separate copy of the source evidence for this delivery, matching recordings and the entry points they reach, and unresolved work. Do not overwrite a prior delivery's evidence with the next span. A ready delivery can be integrated; it has not yet been accepted or counted as measured progress. Make corrections in new commits. Do not amend a submitted snapshot. The message also states what work or investigation the worker will take next, or the concrete blocker if none is available. Submit a ready delivery even if the next work has not been decided.

First submit the delivery with worker-state.mjs submit; --help describes the context, evidence and check-result files. The command derives commits and paths from Git and saves an immutable evidence copy in the shared inbox. Then send READY_TO_MERGE through the callable collaboration tool. In Codex, collaboration tools are separate from functions.ALL_TOOLS. If the notification cannot be sent, the delivery remains submitted and the worker can continue independent work.

The orchestrator records receipt of the exact SHA with a received event, acknowledges it as QUEUED_FOR_MERGE, and integrates each request separately. It sends ACCEPTED with the tested integration SHA and checkpoint result after validation, or CHANGES_REQUIRED with concrete findings. The orchestrator reports publication and CI completion separately. An acknowledgement does not mean acceptance. Workers may continue independent work before acknowledgement. Never require both workers to be ready before accepting one worker's request.

At a clean boundary, update the worker's branch from validated main using a merge that preserves its history. Preserve pending commits and uncommitted changes; do not reset or discard them to synchronize. The orchestrator accepts exact delivery commits. It prefers a merge when the history contains only intended work and selective cherry-picks when needed to exclude unfinished work. Do not merge a branch tip that is still changing. Revalidate dependent work after an earlier correction.

Before starting or resuming, check for live workers and validation processes. Do not duplicate or disrupt work that is still running. For stopped workers, reuse unfinished changes only when their purpose, scope, and remaining validation are clear. Otherwise abandon those changes and start from validated main. Keep abandoned changes recoverable. Do not treat them as pending work or automatically revisit them in future sessions.

If a bounded run ends, stop new spans including worker-selected continuations, preserve unfinished work and its branch/commit/dirty paths in the local task scratch file, and report remaining process ownership. Do not mark unfinished work complete.

Integration

Integrate ready deliveries one at a time in dependency order. Among independent ready deliveries, prefer the one that became ready first. A higher-ranked goal that is not ready does not block integration of a ready independent goal.

Before each wait and after each completion, run worker-state.mjs next. Process unread deliveries and completed worker turns before waiting again. Record observed turn completion with a turn event, then use followup_task on the same worker when independent work remains. Do not stop a worker's next task when accepting its finished task.

If a worker cannot find a task it can start, find out what is stopping it. Give it the task of removing that obstacle, unless someone is already doing so. The orchestrator handles merge problems and decides who may edit shared code. If the worker must wait, record what it is waiting for and who will resolve it. Resume the worker when the obstacle is gone. Do not keep asking it to search the same unchanged queue.

  1. Use node scripts/goal-log.mjs --current --detail to find any goal already open in the central records and its queued span. Identify the exact delivery and checkpoint that belong to it; do not infer the worker assignment from this command alone. Finish that integration or deliberately park it before opening another. Preserve existing queued and parked work.
  2. Check the delivery against its assignment, current completion evidence, source reservations, and reason for selection. Use the existing goal-log.mjs commands in .agents/selection.md or .agents/divergence.md to queue or open its goal and plan its span. Commit those updates to the central records. Compare the planned source units with the delivery and resolve any differences; do not close unrelated units or count a declaration as verification.
  3. Integrate the fixed delivery commits. Inspect the actual combined diff, coverage of the whole selected source range, callers, and recordings for the entry points. Run the affected focused checks and npm run lint. The orchestrator runs npm run quality and uses .agents/review.md to decide whether the change qualifies for review. Record verified source evidence, then commit the exact combined code to be tested. This committed code is the candidate.
  4. Run worker-state.mjs preflight --task <id> on the committed candidate. Resolve every reported omission and run its listed focused checks before the full checkpoint. When retrying a failed checkpoint, supply its summary with --previous-checkpoint and address every failure it reports. Then run one npm run checkpoint on that candidate under .agents/validation.md. The orchestrator owns it through completion; workers continue independently. Freeze integration HEAD until evidence, score recording and closure are complete. When tests fail after a merge, assign a worker to find and fix the cause, then test the corrected code. Other workers continue their tasks. Before keeping work on hold because of an earlier failure, check current main and its saved test results: is the problem already fixed? If so, complete the usual acceptance checks and update the task records. Keep the original failed test result unchanged. Use saved test results to record tests that already finished. If the task tracker rejects the update, report the command and error rather than repeating those tests. A merge without conflicts still needs the required tests.
  5. After a passing checkpoint, start node scripts/mismatch-queue.mjs --json. Use the checkpoint's saved summary for scores. Close the span and append its SCORE.tsv row following .agents/scoring.md. Before closing a source goal, verify every entry point, evaluate frozen challenge set v1, and append the goal score. When closing that source goal, use the current saved development scan. Commit closure and investigation updates together without an intervening change to checkpoint inputs. For a goal with multiple spans, record the intervals when that goal is open for integration so another delivery's gains are not credited to it. If the goal needs more spans, keep it open only while integrating that goal, and park it before measuring another goal. Its worker can continue independently.
  6. Fast-forward main and push accepted work, subject to publication permissions. If permission is missing, retain the validated local commit and ask; do not retry a denied publication without new authorization. Use worker-state.mjs sync-main --commit <accepted-commit> for the local fast-forward. Record published only after the push succeeds; the command verifies both local main and the remote main commit. Watch each relevant CI run once by its exact commit/run ID. CI failure requires diagnosis and a corrected validated commit; workers continue independent work meanwhile. Do not claim CI passed before its run ends.

Keep background investigations running. When node scripts/mismatch-queue.mjs --json finishes, reconsider the reservations. Assigning work on a worker branch does not overwrite the integration branch's investigation cache, which identifies results by session and remaining-screen count. Skip new investigations when the current work completes the user's bounded objective. When all 44 sessions match and goal-log.mjs roadmap lists no unverified C or Lua units, stop and report the complete port.

When a correctness review is warranted, run it as part of the loop over a fixed range of commits. Exclude later commits from that review. Stop or ask only under the user's bounds, publication restrictions, and AGENTS.md's stop conditions. Do not end a continuous loop merely to report progress.

Worker support

If the handoff leaves a broad, unresolved question about callers or dependencies across files, start one read-only survey helper at substantially the same time as the span worker. Tell both agents their responsibilities. The worker owns the complete source comparison, implementation, focused tests, recordings, and commits. The helper owns only the named survey and returns concise file and function pointers plus the contracts they preserve. The helper does not edit files or run a recorder, full suite, checkpoint, or scorer. Forward its findings while the worker can still use them. Have the worker verify each pointer before relying on it. Skip the helper when the symbol and callers are local or already known, a prior investigation settled them, or implementation cannot proceed independently. Record the agents' start and finish times, which findings the worker used, duplication or rework, and handoff overhead.

When a confirmed difficult mismatch has two specific explanations that can be disproved, start at most two read-only investigators at the same time, one for each explanation. The span worker remains responsible for implementation and focused validation. This also applies when one focused investigation has not resolved the mismatch after two probes based on the source and the orchestrator can then state two distinct explanations. Give each investigator a narrow list of permitted source files and artifacts. Tell it what would disprove its explanation. The investigator must stop when its explanation is disproved and return concise source pointers and evidence. It must not edit files, enumerate session corpora, record a session, or run a full suite, checkpoint, or scorer. Forward each verified result as soon as the worker can use it. Stop the remaining investigation if the worker resolves the mismatch first. Skip these concurrent investigations when the cause is already source-local, the explanations are not distinct, or implementation cannot proceed independently. Record the investigators' start and finish times, overlap with implementation, the accepted and rejected explanations, findings used by the worker, duplication or rework, and handoff overhead.

While the worker runs, follow the waiting rules in the shared instructions' "Operational Workflow" section. Wait with notification-aware waits of at most 60 seconds; process any ready delivery or free worker slot before waiting again. Track elapsed time across waits.

After ten minutes without an update, inspect the worker transcript. If it has new events, an active tool call, or a retained process handle, wait for another ten minutes using the same bounded waits. If the transcript has not changed and has no active tool call or retained process handle, wait 60 seconds to confirm. If the transcript still has not changed and the worker is idle, call followup_task with its existing path. If collaboration still reports the worker as running, call interrupt_agent once, then call followup_task with that same path.

When AGENTS.md, this file, or their references already answer a question, state the decision, cite the rule, and continue. Handle every other question according to what it blocks:

  • If it blocks nothing, append the question and provisional decision to .agents/questions.md and continue.
  • If it blocks only the current span, park the span. The worker reports what blocked it without committing. Append the question to .agents/questions.md, send a push notification, and take the next span or goal.
  • If it blocks every next step, follow AGENTS.md's stop cases.

Entries stay open until the user answers. Open each progress report with the count of open entries and the newest one.

Start the two persistent workers at loop entry or resume them after recovery. Spawn other subagents only at the support or investigation step that calls for them. A ready-to-merge message does not require replacing its worker.

When the loop runs under /loop, use completion notifications to continue work already underway. When ScheduleWakeup is available, set it to ten minutes for recovery and use a short interval when idle. End the loop with ScheduleWakeup stop only for AGENTS.md's stop cases. Running low on context is not a reason to stop.

Background investigations

At loop entry and after each queue refresh, follow the session order and cache rules in .agents/selection.md. For every mismatching session without a valid completed investigation, start or continue a source investigation in a subagent. Exclude sessions owned by active workers or pending deliveries. Reserve both implementation slots and slots for any helper required by the workers' current work. Run investigators concurrently in the remaining slots. When those slots are full, queue the remaining sessions in the same order and start the next as a slot becomes available. Keep only one investigator per session. Reuse partial findings when continuing an investigation.

Give each investigator its session, remaining-screen count, examined commit, queue entry, existing artifacts, and any partial cache entry. Require the investigator to read .agents/selection.md, "Investigation cache", for the exact field names and types. Do not substitute an abbreviated schema in the handoff. The investigator reads source and artifacts and may replay its assigned session under .agents/validation.md. It must read source at the examined commit with git show or an existing worktree; it must not mix findings from a changing working tree into that commit's evidence. It identifies the source owner, branch and preconditions, callers, dependencies, and goal scope. It may write only its assigned investigations/<session>.json file and diagnostic artifacts for that session under .cache/. It does not edit game code, instructions, GOALS.json, or score records. The orchestrator handles commits and pushes. The investigator does not scan other sessions, record C runs, or run a full suite, checkpoint, or aggregate scorer.

Have each investigator write its result using the schema in .agents/selection.md. It writes a temporary file beside its assigned cache file, then renames it into place before sending its completion message. The message must include the assigned count and cache path.

Call readInvestigation(root, queueEntry) from scripts/investigation-cache.mjs with the assigned session and count. Require a complete or partial status. Repair a malformed result from the existing findings without repeating the investigation. The orchestrator publishes results as .agents/selection.md specifies. If a scan changes the count during an investigation, stop or finish the old assignment before starting its replacement. Do not accept the old result for the new count or let it overwrite a newer result.

Use completion notifications to collect results and refill available slots. When implementation can proceed from a valid completed investigation, proceed without waiting for other investigators. When none is ready, wait for a completion, check the cache and current session order, and begin implementation as soon as one qualifies. A partial result stays queued for continued investigation. Do not wait for the whole investigation batch before choosing work. Pass reused source findings to the worker and verify them as the normal source review requires.

Reports

Under /loop, send one report per worker iteration. Include the span that closed, the development score before and after, newly matching recordings, the relevant first mismatch before and after, any bug the worker hit, and which span or goal the loop takes next.

Use git diff --name-only --diff-filter=A <span-start>..HEAD -- recordings to identify new recordings; a passing checkpoint confirms they match. New coverage can leave the score unchanged.

Report recovered regressions separately from newly earned screens. Never describe queue upper bounds as delivered or expected gains. Every aggregate figure must come from the exact combined checkpoint. Do not use worker-branch totals as delivered progress. A parked goal's delivered count includes only its active intervals; gains while another goal runs belong to that goal.

Report ready, integrating, validated, published and CI-complete states separately. Include the next assignment for each free worker slot, any wait for dependencies, and any integration work that must be redone. Do not count time in the validation queue as idle time when a worker is coding.

Keep updates brief and specific: report changed behavior, remaining work, and the next check when useful. Do not repeat unchanged status. When switching between implementation, validation, and review, state the switch and the reason once. Review reports follow .agents/review.md.
